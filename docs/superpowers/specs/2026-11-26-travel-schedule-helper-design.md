# 여행 일정 도우미 기획안

- 작성일: 2026-11-26
- 상태: 초안 (검토 전)
- 근거 자료: 사용자가 제시한 DB 설계안, `index.html`(Gemini Canvas가 만든 샘플 일정), `data/trip-pt-es-honeymoon.verified.json`(웹 검색 검증 결과)

표기: **[결정]** 은 대화에서 사용자가 정한 것, **[제안]** 은 작성자가 정한 것으로 바꿀 수 있습니다, **[미정]** 은 사용자 답이 필요한 것입니다.

## 1. 무엇을, 왜 만드는가

회원 취향과 여행 조건을 넣으면 일차별 일정을 짜 주고, 그 일정의 **장소와 이동 방법이 실제로 맞는지 검증**해서 보여 주는 앱입니다.

Gemini Canvas에 간단히 물어도 일정은 나옵니다. 하지만 그 결과는 AI가 쓴 글을 정적 페이지로 만든 것이라 검증이 없습니다. 샘플 일정 56개 항목 중 19개를 웹 검색으로 확인했더니 7개가 일정대로는 실행할 수 없었고 4개는 값이 틀렸습니다.

| 유형 | 샘플에서 나온 예 |
|---|---|
| 요일 휴무 | 화요일 휴무 식당을 화요일 저녁에 배치 |
| 방문 시각과 영업시간 불일치 | 18:00에 닫는 곳을 18:00에 방문 |
| 임시 폐쇄 | 보수 중인 탑, 정비 중인 엘리베이터 |
| 지역 행사 | 세비야 체류가 세마나 산타와 겹침 |
| 이벤트 일정 | 축구 직관일에 홈경기 없음 |
| 낡은 값 | 택시 정액 요금 30유로(실제 33유로) |
| 규정 변경 | 동굴 내부 상륙 금지 |

문제 대부분은 장소가 틀린 것이 아니라 **날짜·시각과 맞지 않는 것**이었습니다. 이 앱이 Gemini에 그냥 물어보는 것보다 나아야 할 지점이 여기입니다.

## 2. 목표와 범위

**목표**

1. 프로필 기본값 + 여행별 오버라이드로 조건을 한 번만 입력하게 한다. **[결정]**
2. 조건에 맞는 일정을 일차별 타임라인 카드로 만든다. **[결정]**
3. 카드마다 대안 장소를 두고 교체(스왑)할 수 있게 한다. **[결정]**
4. 모든 카드와 이동 구간에 검증 상태·근거·확인 시각을 붙인다. **[결정: 검증 필요 / 제안: 표현 방식]**
5. 일정 1건을 만드는 데 드는 토큰과 비용을 측정한다. **[결정]**

**하지 않는 것 (1차 범위 밖)** **[제안]**

- 예약·결제 대행
- 항공권·숙소 가격 비교
- 실시간 위치 추적, 내비게이션
- 여러 명의 실시간 공동 편집 (공유 보기까지만)

**실패로 보는 경우**

- 검증되지 않은 내용을 검증된 것처럼 보여 주는 것. 확인 못 한 항목은 "미검증"으로 표시합니다.
- 일정 1건 비용을 모르는 채로 사용자에게 여는 것.

## 4. 구현 방식 비교

| | A. AI만 사용 | B. AI 초안 + 검증 단계 | C. 자체 장소 DB 우선 |
|---|---|---|---|
| 방식 | AI가 일정을 쓰고 그대로 표시 | AI가 초안을 쓰고, 별도 단계가 항목별로 사실을 확인 | 장소를 먼저 수집·큐레이션하고 규칙으로 필터링해 조합 |
| 장점 | 가장 빠르고 쌈 | 어느 지역이든 동작, 오류를 잡음, 검증 수단을 교체 가능 | 웨이팅·주종 같은 고유 필터가 정확 |
| 단점 | 샘플에서 본 오류가 그대로 나감 | 호출이 늘어 비용 증가 | 지역마다 데이터를 먼저 쌓아야 해서 시작이 느림 |

**B를 권합니다. [제안]** A는 Gemini Canvas와 같은 결과라 만들 이유가 없고, C는 데이터가 쌓이기 전에는 쓸 수 없습니다. B로 시작하고, 사용자가 확정한 장소와 검증 결과를 `places`에 쌓아 가면 자주 가는 지역부터 C의 장점을 얻습니다.

## 5. 구조

```
조건 병합 ──→ 초안 생성 ──→ 검증 ──→ 보정 ──→ 저장·표시
(프로필+여행)   (LLM)      (검증 공급자)  (LLM: 문제 항목 교체)
                              │
                 ┌────────────┴────────────┐
           1단계: 웹 검색            2단계: Google API
           (Claude 웹 검색)       (Places, Routes)
```

검증은 **공급자 인터페이스** 하나로 두고 구현을 바꿔 끼웁니다. **[제안]** 그래야 같은 여행 조건으로 1단계와 2단계의 정확도·비용을 비교할 수 있습니다.

**검증 항목**

| 검사 | 1단계 웹 검색 | 2단계 Google API |
|---|---|---|
| 실존·폐업 | 가능 | Places |
| 요일 휴무, 방문 시각과 영업시간 | 가능(출처 엇갈림 있음) | Places |
| 임시 폐쇄·보수 | 가능 | Places(일부) + 웹 검색 |
| 지역 행사·공휴일·경기 일정 | 가능 | 제공 안 함 → 웹 검색 유지 |
| 좌표, 반경, 도보 거리 | 불가 | Places + Routes |
| 구간 이동 시간 | 대략만 | Routes |
| 날짜별 열차·버스 출발편 | 불가에 가까움 | Routes(대중교통, 지역별 차이) |
| 요금·규정 변경 | 가능 | 제공 안 함 → 웹 검색 유지 |

2단계에서도 웹 검색은 없어지지 않습니다. 행사·경기·규정은 지도 API가 주지 않습니다.

**검증 상태** (시드 파일과 동일): `verified` 일치 / `corrected` 값이 틀려 고침 / `problem` 일정대로 실행 불가 / `partial` 일부만 확인 / `unverified` 확인 안 함.

검증 단위는 장소가 아니라 **"장소 + 방문 일시"** 입니다. 같은 식당도 화요일 저녁이면 문제이고 수요일이면 정상입니다.

## 6. 데이터 모델

사용자 설계안(`users`, `user_profiles`, `trips`, `places`, `trip_items`, PostgreSQL + PostGIS + JSONB)을 그대로 쓰고 아래를 더합니다.

### 6.1 고치는 것

**조건 병합 규칙.** `default_prefs || pref_overrides`는 얕은 병합이라 규칙을 명시합니다. **[제안]**

- 키가 없으면 프로필 기본값을 따른다.
- 키가 있으면 그 값으로 교체한다. 배열은 합치지 않고 통째로 교체한다.
- 값이 `null`이면 "이번 여행은 제한 없음"이다.
- 일정을 생성할 때 병합 결과를 `trips.effective_prefs`에 저장한다. 나중에 프로필을 바꿔도 이미 만든 일정의 근거가 변하지 않는다.

**`places`와 구글 데이터.** 구글 Places 데이터는 `place_id` 외에는 장기 저장이 제한됩니다(좌표는 단기 캐시만 허용). 그래서 한 테이블에 섞지 않고 나눕니다. **[제안, 약관 원문 확인 필요]**

- `places`: 자체 식별자, 이름, 카테고리, `google_place_id`, 직접 확보한 좌표(`location`, 출처 표시)
- `place_provider_cache`: 공급자에서 받은 영업시간·좌표 등, `fetched_at`, `expires_at`
- `place_attributes`: 구글이 주지 않는 고유 속성(평균 웨이팅, 주종·분위기 태그, 주차). 값마다 출처(`curated`/`user_report`/`llm_extracted`)와 확인 시각

**`alternative_place_ids` 배열 → 테이블.** UUID 배열은 FK가 걸리지 않고 대안별 메모·순위를 담지 못합니다. `trip_item_alternatives(item_id, place_id, rank, reason)`로 바꿉니다. **[제안]**

### 6.2 추가하는 것

| 테이블 | 용도 | 주요 컬럼 |
|---|---|---|
| `trip_legs` | 카드 사이 이동 구간 | `from_item_id`, `to_item_id`, `mode`, `duration_min`, `distance_m`, `cost`, `source` |
| `verifications` | 검증 기록 | `target_type`(item/leg/trip), `target_id`, `check_type`, `status`, `finding`, `sources`(JSONB), `provider`, `checked_at`, `expires_at` |
| `llm_usage_log` | 토큰·비용 측정 | `trip_id`, `step`, `provider`, `model`, `input_tokens`, `output_tokens`, `search_count`, `api_calls`, `cost`, `created_at` |
| `trip_members` | 동행자·공유 | `trip_id`, `user_id`, `role`(owner/viewer) |
| `swap_history` | 스왑 이력 | `item_id`, `from_place_id`, `to_place_id`, `reason`, `swapped_at` |

`trip_items`에 추가할 컬럼: `start_at`/`end_at`(시간대 포함), `timezone`, `status`(planned/confirmed/skipped), `reservation_status`, `currency`.

`trips`에 추가할 컬럼: `effective_prefs`, `anchor_item_id`(반경 검색 기준이 되는 숙소), `base_currency`.

## 7. 토큰·비용 측정

- 모든 LLM·API 호출을 `llm_usage_log`에 단계별(`draft`/`verify`/`repair`)로 기록합니다.
- 보는 지표: 일정 1건당 총 토큰, 검색 횟수, 항목 1개당 검증 비용, 단계별 비중.
- 지금 가진 기준치: 19개 항목 검증에 검색 16회, 검색 결과 분량 약 3~4만 토큰(추정). 정확한 수치는 1단계 스크립트에서 응답의 사용량 값으로 잽니다.
- 비용을 줄이는 방법: 날짜에 민감한 항목(식당 휴무, 행사, 이동편)을 먼저 검증하고, 같은 "장소 + 날짜" 검증은 `expires_at`까지 재사용합니다.

## 8. 진행 단계

| 단계 | 내용 | 끝났다고 보는 기준 |
|---|---|---|
| 0 | 웹 검색으로 샘플 검증 | 완료 (`data/trip-pt-es-honeymoon.verified.json`) |
| 1 | Claude API + 웹 검색 스크립트: 조건 → 초안 → 검증 → 시드와 같은 형식의 JSON, 사용량 기록 | 샘플 여행을 다시 돌려 일정 1건당 토큰·비용이 나옴 |
| 2 | Google API 키 연결: Places·Routes 검증 공급자 추가 | 같은 여행으로 1단계와 정확도·비용 비교표가 나옴 |
| 3 | 앱: 화면 1~9(3.1절), DB. 지도는 2단계 공급자를 씀 | 한 사용자가 가입부터 스왑까지 끝낼 수 있음 |
| 4 | 화면 10(공유), 동행자 취향 합치기 | 범위는 3단계 이후 다시 정함 |

1단계는 Anthropic API 키, 2단계는 결제가 설정된 Google Cloud 프로젝트의 API 키가 필요합니다.

## 9. 사용자 답이 필요한 것

1. **국내와 해외 중 무엇이 먼저인가.** **[미정]** 설계안의 태그(소주·청하, 1차·2차·해장)는 국내 여행을 가리키는데 샘플은 해외입니다. 한국에서는 구글 지도의 도보·자동차 길찾기가 제한되어 왔고 장소 정보도 카카오·네이버보다 얕습니다. 국내가 먼저라면 2단계 공급자를 구글이 아니라 카카오·네이버로 잡아야 할 수 있습니다. 현재 상태는 확인이 필요합니다.
2. **웨이팅·주종·분위기 값은 어디서 얻는가.** **[미정]** 직접 큐레이션, 리뷰에서 AI로 추출, 사용자 제보 중 무엇으로 시작할지.
3. **본인용인가 공개 서비스인가.** **[미정]** 공개라면 3단계에 가입·권한·비용 상한이 들어가고, 본인용이면 생략할 수 있습니다.
4. **앱 형태.** 모바일 화면에 맞춘 웹 앱(PWA)을 제안합니다. **[제안]** 지금 결과물이 React 웹이라 이어 쓰기 쉽고, 스토어 심사 없이 바로 써 볼 수 있습니다. 네이티브 앱이 필요하면 알려 주세요.
